L4 讲解：plan_slab 怎样把一张图塞进一块内存

用不融合的 relu(x @ w + b) 计划，把参考解（也是 Luminal arena.rs 的移植）一步一步跑出来：传递闭包、precedes 判定、first fit 怎样把 t1 和 y 塞进 x 腾出的空间；画出 slab 的布局；再把一次执行拆成四个阶段，并对照 Luminal 的 trace 环境变量。

② precedes：每一个使用都在前面

drillsreachability（46–55 行） 倒着拓扑序求闭包：after[lt_matmul] = {add_bias, relu, readback}。precedes(a, b) 要求 a 的每个使用都能到达 b 的每个使用：

对 判定 能共用？

t0 → y {lt_matmul, add_bias} 都能到 {relu, readback} ✔

slab_bytes = 1,196,288 B（高水位由 t0 的末尾决定）；不复用时 1,229,056 B。workspace 占了大头，所以这个小例子里复用只省了 32 KiB；在真实模型里，几十层的激活值轮流复用同一块内存，差距是几倍。

类比 · 停车场

slab 是一排车位，buffer 是车，uses 是停车时段。两辆车能先后用同一个车位，当且仅当一辆完全开走之后另一辆才来。first fit 就是“从最左边开始找第一个空位”。它不保证全场最省，Luminal 的注释说得很诚实：容量错误只意味着“这个算法没找到摆法”，不意味着不存在摆法。

④ 为什么是 DAG 可达性，而不是时间线

一个直接的想法是按拓扑序给节点编号，用 [第一次使用, 最后一次使用] 区间判断重叠。但这会发明一个执行顺序：两个并行分支 b、c 在拓扑序里一前一后，区间不重叠，就会被安排共用内存——一旦运行时让它们并行（不同 stream、CUDA graph 里的并行节点），数据就互相覆盖。arena.rs 的注释特意强调“Transitive closure of the supplied dependency DAG, never an invented topological execution order”。测试 test_unordered_branches_cannot_alias 就是这个菱形 DAG。

⑤ 四个阶段

drillsphase_breakdown / achieved（141–156 行）：测试的例子里 graph_compile 0.4 s、search 3.0 s、prepare 0.1 s、两次 execute 各 0.5 ms——search 占 85.7%。这就是为什么 L3 要算 break-even，也是为什么 README 把 LUMINAL_CUDA_PROFILE_RECAPTURE 描述为“decomposing TTFT/TPOT into kernel time vs. runtime overhead”的工具。

achieved(2·64·64·256, 10 µs, 40 TFLOP/s) = 0.21 TFLOP/s，峰值的 0.5%：小 GEMM 是 launch-bound，和 K1 的 roofline 一致。

⑦ 自测

把请求顺序改成先放 t1、y，再放 x，slab_bytes 会变吗？

在这个例子里不变：t1、y 先放在 0 和 16,384，之后 x 和它们“严格先后”，仍然可以放在 0，最终 slab 还是 1,196,288 B（自己跑一下就能确认）。但一般会变：first fit 是按请求顺序的贪心，先放的占据低地址，顺序不同，后来者能找到的空隙就不同。Luminal 的文档说“The result follows request order”，所以请求顺序本身是计划的一部分。

融合计划（一个 cuBLASLt RELU_BIAS 调用）的 slab 为什么和不融合的一样大？

两者的高水位都由 x + w + b + workspace + 一个 [M, N] 输出 决定：不融合时 t1、y 复用了 x 的地盘，没有抬高高水位。融合省下的是两次 launch 和 t0/t1 的 DRAM 往返，而不是峰值内存。如果 workspace 很小、激活很大，结论会不同——用 plan_slab 换参数试试。
