lede: Triton 的 coalesce pass 为每个 load / store 挑一个 BlockedEncoding。这道题用 Python 逐行复刻它的两段真实代码，输出要和 coalesce.mlir 的 CHECK 逐字一致；然后用这个 layout 回答 T2 的三个问题：每个 lane 负责哪些坐标、load 是否合并访存、一次 convert_layout 是寄存器重命名、warp shuffle 还是要过 shared memory。

## 背景

roadmap 的 T2：“选 2D blocked layout，改变 size-per-thread、threads-per-warp、warps-per-CTA；手算每个 lane 负责哪些坐标；分析 global load 是否 coalesced；制造一个 layout conversion，观察 shared memory / shuffle 是否出现。交付：lane-coordinate 表 + PTX / TTGIR 对照。”

与其凭感觉改参数，不如直接看编译器怎么选：`tritongpu-coalesce` 这个 pass 决定了绝大多数 load / store 的 layout，而它的核心只有两段几十行的代码。

## 要用到的知识：coalesce pass 的两步

**第一步：每线程几个元素（perThread）**

```text
elem_bytes   = elem_bits / 8
max_multiple = divisibility_bytes / elem_bytes        # 指针对齐允许的最大向量
max_contig   = min(contiguity, shape[order[0]])       # axis analysis 证明的连续长度
perThread    = min(max_multiple, max_contig, 128 / elem_bits)   # 一条指令最多 128 bit
perThread    = min(perThread, max(numElems / numThreads, 1))    # 别让线程没活干
sizePerThread = [1, ..., perThread (在 order[0] 维), ..., 1]
```

**第二步：分 lane 和 warp（BlockedEncodingAttr builder）**

```text
rem_lanes, rem_threads, rem_warps = 32, num_warps*32, num_warps
for d in order[:-1]:                                   # 从最快维开始，最慢维除外
    threads_cta = clamp(rem_threads, 1, max(1, shape[d] / spt[d]))
    tpw[d]      = clamp(threads_cta, 1, rem_lanes)
    wpc[d]      = clamp(threads_cta / tpw[d], 1, rem_warps)
    rem_*      /= ...
tpw[order[-1]] = 32 / (前面各维 tpw 之积)                # 最慢维拿走剩下的 lane 和 warp
wpc[order[-1]] = num_warps / (前面各维 wpc 之积)
```

**手算 coalesce.mlir 的 `@transpose`**（64×64 fp32，`num-warps = 4`，`tt.divisibility = 16`）：

- 读：`order = [1, 0]`，`perThread = min(16/4, 64, 128/32, 4096/128) = 4` → `spt = [1, 4]`。dim 1：`threads_cta = clamp(128, 1, 64/4=16) = 16`，`tpw[1] = 16`，`wpc[1] = 1`；dim 0 拿剩下的：`tpw[0] = 32/16 = 2`，`wpc[0] = 4`。
  结果 `#ttg.blocked<{sizePerThread = [1, 4], threadsPerWarp = [2, 16], warpsPerCTA = [4, 1], order = [1, 0]}>`，**正是测试文件里的 `[[row_layout]]`**。
- 写（转置，`order = [0, 1]`）：同理得到 `sizePerThread = [4, 1], threadsPerWarp = [16, 2], warpsPerCTA = [1, 4]`，即 `[[col_layout]]`。

## 要用到的知识：lane 表、合并访存、convert_layout 的三档代价

- **lane 表**：线程 `(warp, lane)` 的第 r 个寄存器对应的坐标（和 gpu-kernel-drills G1 同一个公式）：`coord[d] = rep[d]·tile[d] + warp_c[d]·spt[d]·tpw[d] + lane_c[d]·spt[d] + s[d]`，再对 shape 取模（张量比 tile 小时会有多个线程持有同一元素）。
- **合并访存**：warp 0 的第一条向量 load，每个 lane 读 `vec = min(spt[order[0]], 16 / elem_bytes)` 个连续元素；数一下覆盖了多少个 32 B sector，效率 = 请求字节 / (sector 数 × 32)。
- **convert_layout 的三档**（Triton 用线性布局精确判断，本题用“元素归属”近似）：

| 档位 | 条件（本题） | Triton 里 | 代价 |
|---|---|---|---|
| `registers` | 每个元素的持有线程集合不变 | `cvtReordersRegisters` | 只是寄存器重命名，0 成本 |
| `warp_shuffle` | 每个元素仍在同一个 warp 里 | `cvtNeedsWarpShuffle`（还要求置换足够简单） | 若干条 `shfl.sync` |
| `shared_memory` | 有元素要跨 warp | `cvtNeedsSharedMemory` | 写 smem → barrier → 读 smem |

::: callout analogy 交接班
一次 layout 转换像两个班次交接工具。每个人手里的工具不变、只是换了个口袋（registers）——零成本；同一个小组内互相递一下（warp shuffle）——很快；工具要交给另一个小组的人（跨 warp），就得先放回公共工具房、等所有人都放好（barrier）、再各自去取（shared memory）——最慢。`remove_layout_conversions` 这个 pass 存在的意义，就是尽量别让工具进工具房。
:::

## 在 RTX 3070 上：TTGIR 与 PTX 对照

1. 用 coalesce.mlir 本身做实验：`triton-opt test/TritonGPU/coalesce.mlir -split-input-file -tritongpu-coalesce`（源码 build 后在 `build/` 下有 `triton-opt`），把输出里的 `#blocked` 和 `coalesced_layout()` 对比；把 `%arg0` 的 `tt.divisibility` 改成 8，预测 perThread 会变成多少，再跑一次验证。
2. 写一个 64×64 的转置 kernel，看 `k.asm["ttgir"]` 里的 `ttg.convert_layout`，再在 `k.asm["ptx"]` 里找 `st.shared` / `ld.shared` / `bar.sync`：你的 `classify_conversion` 说 `shared_memory` 的那次转换，PTX 里应该正好对应一组 smem 写 + barrier + smem 读。
3. 把 `ld.global.v4.f32`（每线程 4 个 fp32 = 16 B）和 `first_load_sectors` 的效率对照：行布局读行主序张量时效率 1.0；拿同一个 layout 去读转置的张量，效率掉到 0.25。

::: answer 自测：为什么 fp16 的 [128, 64] 张量 perThread 是 8 而不是 4？
一条全局访存指令最多 128 bit（`128 / elem_bits`）：fp32 是 4 个，fp16 是 8 个。只要指针 16 B 对齐（`divisibility = 16` → `16 / 2 = 8`）、连续长度至少 8、每个线程平均至少分到 8 个元素（8192 / 128 = 64），perThread 就是 8，对应 PTX 里的 `ld.global.v4.b32`（4 个 32 bit = 8 个 fp16）。
:::
