lede: 搜索选中了一个计划之后，backend 还要做两件事：决定每个 buffer 放在一块设备内存的哪个偏移上，以及按依赖顺序发出 launch。这道题移植 Luminal 的 plan_slab（DAG 可达性 + first fit + 256 B 对齐），把 relu(x @ w + b) 的融合 / 不融合两个计划都排一遍，再把一次执行拆成 graph compile / search / prepare / execute 四个阶段。

## 背景

roadmap 的 L4：“打开 Luminal logging / LLIR dump / CUDA profiling 相关环境变量，跟踪一个 matmul graph；区分 graph compile、candidate evaluation、prepare、execute；识别实际调用的 kernel / library；比较理论 FLOPs 与真实 GPU 时间。交付：一条端到端 trace 注释。”

trace 里最难读懂的一段是内存：一个 finalist 的 `arena.slab_bytes` 就是它的设备内存高水位，finalists.rs 拿它和设备预算比较。这个数来自 [[luminal:src/buffer/arena.rs@pub fn plan_slab|src/buffer/arena.rs 的 plan_slab]]，文档注释写得很清楚：

> Two buffers may alias only if every use of one strictly precedes every use of the other. Unordered branches and operands of the same node cannot alias.

## 要用到的知识

**plan_slab 的三步**

1. 对 DAG 做拓扑排序，倒着求传递闭包：`after[u]` = 从 u 出发能到达的所有节点（真实代码用 64 位 bitset）。
2. `precedes(a, b)` ⇔ a 的**每一次**使用都能到达 b 的**每一次**使用。
3. 按请求顺序逐个放：只有和当前 buffer “互不先后”的已放 buffer 才算占位；把占位区间排序，从 0 开始找第一个放得下的空隙（first fit）。大小先向上对齐到 256 B；空 buffer 也占一个对齐单位。

::: flow 不融合的计划：谁能和谁共用内存
cfg cw=180 nw=150 rh=90
n up 0 0.6 "upload" "" k=ghost w=0.7
n mm 1 0.6 "lt_matmul" "x · w → t0" k=acc
n ab 2 0.6 "add_bias" "t0 + b → t1" k=warn
n rl 3 0.6 "relu" "t1 → y" k=warn
n rb 4 0.6 "readback" "" k=ghost w=0.7
n note 2 1.85 "x 用完了" "t1、y 复用它的字节" k=pass w=1.3
e up -> mm
e mm -> ab
e ab -> rl
e rl -> rb
e mm -> note dash
cap: x 的使用是 {upload, lt_matmul}，t1 的使用是 {add_bias, relu}：每一个 x 的使用都在每一个 t1 的使用之前，所以 t1 可以放在 offset 0。t0 的使用 {lt_matmul, add_bias} 和 x 在 lt_matmul 处重叠，不能共用。
:::

::: callout analogy 会议室排期
slab 是一层楼的会议室走廊，每个 buffer 是一场会，它的 uses 是开会的时间段。两场会能用同一间会议室，当且仅当一场**完全结束**之后另一场才开始（precedes）。两场会只要可能同时进行（DAG 上没有先后：并行的分支），就必须用不同的房间。first fit 就是“从走廊最左边开始，找第一间空着的”。它简单、确定，但不保证最省——文档原话：“A capacity error means this algorithm did not find a placement, not that no possible placement exists.”
:::

## 提示

::: hint 1 reachability 要倒着算
按拓扑序的**逆序**处理节点：`after[n] = ⋃ ({s} ∪ after[s]) for s in dag[n]`。这样处理 n 时，它的所有后继都已经算好了。
:::

::: hint 2 first fit 的循环
```python
off = 0
for start, n in sorted(occupied):
    if off + size <= start: break      # 放进这个空隙
    off = max(off, start + n)          # 跳过这个占位
```
:::

::: hint 3 测试里的两个关键数
链 `a → b → c` 上，p / q / r 各只在一个节点使用，彼此严格先后，所以都在 offset 0；s 跨越 a 和 c，和三者都重叠，放到 `aligned(1000) = 1024`。菱形 DAG 里 b、c 无先后，p、q 必须错开。
:::

## 在 Luminal 里：一条端到端 trace

```bash
LUMINAL_LOG=1 LUMINAL_LOG_LLIR=1 LUMINAL_SEARCH_OP_NAMES=1 \
LLIR_DUMP_DIR=./llir LUMINAL_CUDA_PROFILE_RECAPTURE=1 LUMINAL_CUDA_MEMORY_DEBUG=1 \
cargo run --release -p luminal_cuda_lite --example <your_matmul_example> --features device 2>&1 | tee trace.log
```

在 trace.log 上做注释：

1. **graph compile**：`EGGLOG_LOG` 的 e-graph 构建 / schedule 行。
2. **candidate evaluation**：`SEARCH_LOG` 的进度和 best-so-far 行；`[Kernels: …] [Hosts: …]` 告诉你候选由哪些 kernel / 库组成（是否出现 cuBLASLt）。
3. **prepare / execute**：`CUDA_PREPARE_PROFILE`、`CUDA_EXEC_PROFILE`、`CUDA_ALLOC_PROFILE` 行，填进 `phase_breakdown`。
4. **内存**：`llir/` 里选中 finalist 的 `.txt` / `.dot`，和 `LUMINAL_CUDA_MEMORY_DEBUG` 的 arena 统计；用 `plan_slab` 复算一个小图的 slab，对上 `slab_bytes`。
5. **理论 vs 实测**：`achieved(2·M·N·K, kernel_seconds, peak)`。64×256×64 这种小 GEMM 只能达到峰值的零点几个百分点——launch-bound；换成 4096³ 再看。

::: answer 自测：为什么“同一个节点的两个操作数”不能共用内存，即使它们都只在这个节点被用到？
对同一个节点 v，`precedes(a, b)` 要求 a 的使用 v 严格先于 b 的使用 v，也就是 v 能到达 v——在 DAG 里不可能。所以两者互不先后，必须放在不同的地址。这符合直觉：kernel 运行时要同时读两个操作数，它们当然不能占同一块内存。
:::
