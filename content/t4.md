lede: 维护者最欢迎的 issue 是一个“十行能复现”的最小例子。这道题写出产出它的完整流水线：固定 seed 的随机差分测试 → 保留第一个失败输入 → 把形状、dtype、stride 缩到最小 → 自动生成可以直接提交的 pytest 回归测试。顺带实现 delta debugging，用来缩小 IR 和图。

## 背景

roadmap 的 T4：“对一个 op / layout / dtype 构造随机差分测试，覆盖非整除 shape、mask、FP16 / BF16 边界和非连续 stride；写 PyTorch reference；固定 seed，保留失败输入；缩小到最小 shape / dtype / layout reproducer。交付：可直接转成 pytest / lit regression 的最小案例。”

被测对象 `buggy_row_sum` 是一个“分块求和 kernel”，带着一个经典 bug：单块路径做了 mask，多块路径只走完整的块、忘了尾巴。随机测试能撞到它，但撞到的输入（比如 `[129, 255]`、bf16、转置 stride）离“最小”很远。

**两种缩小**

- **结构化**（`shrink_case`）：对每一维用 `shrink_int` 找“仍然失败的最小值”（先试减半，再减 1）；再按 `float32 → float16 → bfloat16` 尝试更简单的 dtype；再试连续 stride。直到一整轮都没有变化（fixpoint）。
- **列表**（`ddmin`）：输入是一串东西（IR 的行、图的节点、一组 rewrite 规则），把它切成 n 块，试“只保留某一块”或“去掉某一块”，能缩就缩、不能缩就切得更细。结果是 **1-minimal**：再删掉任何一个元素就不再失败。

::: callout analogy 找出是哪道菜让人过敏
一桌 20 道菜吃完过敏了。ddmin 的做法：先只吃前 10 道，没事？那问题在后 10 道或者两部分的组合里；再分成 4 份试……最后发现是“3 号菜 + 17 号菜”一起吃才过敏（测试里的 `[3, 17]`）。结构化缩小则像减量：先吃一半份量还过敏吗？再少一口呢？直到找到最小的那一口。
:::

## 提示

::: hint 1 shrink_int
```python
while n > lo:
    half = max(lo, n // 2)
    if half < n and fails(half): n = half
    elif fails(n - 1): n -= 1
    else: break
```
注意它假设“失败的 n”大致单调；对 `n % 64 != 0 and n > 64` 这种不单调的条件，减半会失败，逐个减一仍然能找到 65。
:::

::: hint 2 ddmin 的骨架
`n = 2`；循环：切成 n 块；有某一块单独失败 → 换成它、`n = 2`；有某个补集失败（块数 > 2 时）→ 换成补集、`n = max(n − 1, 2)`；都不行 → 若 `n ≥ len(items)` 结束，否则 `n = min(2n, len)`。
:::

::: hint 3 to_pytest 必须真的能跑
测试会 `exec` 你生成的代码：用 buggy 实现时它必须失败，用正确实现时必须通过。非连续的 case 用 `rng.standard_normal((n, m)).T` 生成输入，和 `make_input` 保持一致。
:::

## 在 RTX 3070 上：换成真的 Triton kernel

把 `buggy_row_sum` 换成一个真实的 Triton 行求和（自己故意写错尾部 mask，或者挑一个你怀疑的 op，比如某个 dtype 的 `tl.cumsum`），`impl = lambda x: triton_row_sum(torch.from_numpy(x).cuda()).cpu().numpy()`，其余代码不变。找到真 bug 时，把 `to_pytest` 的输出改写成 `test_core.py` 的风格（`@pytest.mark.parametrize` 形状和 dtype，`device` fixture），附上 `git rev-parse HEAD`、GPU 和 Toolkit 版本，就是一个合格的 issue。如果你已经定位到某个 pass，用 `MLIR_ENABLE_DUMP=1` 拿到出错前的 TTGIR，用 `ddmin` 缩小它，再写成 T5 那样的 lit 测试。

::: answer 自测：为什么要先简化 dtype，再试连续 stride？
每一种简化都去掉一个“可能的原因”。如果 fp32 + 连续 stride 还能复现，维护者马上知道问题与低精度、与非连续访存无关，只与形状有关；反过来，如果只有 bf16 才失败，那 bug 很可能在类型转换或累加精度上。最小案例的价值不仅是短，更是它**排除了多少假设**。
:::
