lede: roadmap 说“最好的共同实验”是同一组 GEMM / fused MLP workload 两边各走一遍：先用 Triton 写出并 profile 一个 kernel，理解它的硬件成本；再看 Luminal 的 graph / search 如何为同一个计算选择执行实现。这是一个实践页，没有 check.sh，产出是一张对照表和一页分析。

## 实验设计

**workload**：`y = relu(x @ w + b)`，fp16 输入、fp32 累加、fp16 输出；三个形状：

| 名字 | M × K × N | 代表什么 |
|---|---|---|
| decode | 16 × 4096 × 4096 | 小 batch 推理：memory / launch-bound |
| prefill | 2048 × 4096 × 4096 | 大 batch：compute-bound |
| odd | 1000 × 4095 × 1000 | 非整除：mask、tail、对齐 |

## Triton 一侧

1. 在 tutorial 03 的 `matmul_kernel` 里加 `+ bias` 和 `relu` 的 epilogue（tutorial 已有 `ACTIVATION="leaky_relu"` 的例子）。
2. 正确性：K3 的 `check_close`，容差 `tolerance("float16", K)`。
3. 用 T3 的 `autotune` 扫三个形状，存 CSV；记录最佳配置的 `n_regs`、`n_spills`、`metadata.shared`。
4. 用 T1 的工具数 PTX 里的 `mma.sync` 和 `ldmatrix`，看 TTGIR 里 `ttg.convert_layout` 出现在哪。
5. 用 K1 的 `analyze` 算理论时间，和实测比较：decode 形状离 roofline 有多远？为什么？

## Luminal 一侧

1. 写同一个图（L1 的 Rust 片段），在 ReferenceRuntime 上和 Triton 的结果对拍。
2. CUDA 编译，打开 `SEARCH_LOG=1 LUMINAL_SEARCH_OP_NAMES=1 LUMINAL_LOG_LLIR=1`：搜索选中的是 cuBLASLt（带 `RELU_BIAS` epilogue？）、自己生成的 kernel，还是多个 launch？
3. `LUMINAL_CUDA_PROFILE_RECAPTURE=1`：execute 时间里，kernel 本身占多少，runtime 开销占多少？
4. 把编译 + 搜索时间单独记下，算 L3 的 break-even：执行多少次之后，Luminal 的搜索成本被摊平？

::: callout analogy 同一道菜，两种考法
Triton 一侧像考厨师的刀工：给你一道菜（一个 kernel），看你切得多细、火候多准（tile、layout、MMA）。Luminal 一侧像考主厨的统筹：同一道菜，是自己做还是用中央厨房的半成品（cuBLASLt），和别的菜怎么排（执行计划），整桌菜多久上齐（端到端）。两张成绩单放在一起，才知道这道菜的瓶颈在“切”还是在“排”。

## 分析要回答的问题

- 三个形状下，Luminal 选中的实现和 Triton 最佳 kernel 谁快？差距来自 kernel 本身，还是 launch / runtime 开销？
- decode 形状下，两边是不是都被 launch 开销主导？CUDA graph（Luminal 的 `cuda_graph.rs`）有没有起作用？
- odd 形状下，Triton 的 mask 和 Luminal 的选择各付出了多少代价？
- 如果 Luminal 选了 cuBLASLt：如果你的 Triton kernel 更快，那 Luminal 的搜索空间里缺了什么？这可能就是一个 issue（Week 13 的“深水区”候选）。

::: answer 自测：为什么要把 compile / search 时间单独一列？
Triton 的 JIT + autotune 和 Luminal 的 e-graph + 搜索都是一次性成本，量级可能是秒到分钟；execute 是稳态成本，量级是微秒。混在一起报告，小 workload 上会得出“Luminal 慢一万倍”这种无意义的结论。分开报告，再用 break-even 把两者联系起来，才是 roadmap 要求的“compile 与 runtime 分离”。
:::
