lede: Triton 的编译器测试几乎都是“一个 .mlir 文件 + 一行 RUN + 一串 CHECK 注释”。这道题自己实现一个 FileCheck（CHECK / NEXT / SAME / NOT / LABEL / DAG / COUNT、{{regex}}、[[VAR:regex]] 捕获与引用），然后你就能读懂、也能写出 Triton 的 lit 测试——这是最稳妥的第一笔贡献。

## 背景

roadmap 对 Triton 贡献的建议：“最稳妥的第一步是补一个能稳定失败 / 通过的 regression test，再提交针对性修复。”Week 7 的任务是“读 lit / FileCheck 与 Python tests”。

一个 lit 测试的执行过程：

```text
// RUN: triton-opt %s -split-input-file -tritongpu-coalesce | FileCheck %s
```

1. lit 把 `%s` 换成这个文件的路径，执行 RUN 行：`triton-opt` 对文件跑 `tritongpu-coalesce` 这个 pass，输出变换后的 IR。
2. 输出通过管道交给 `FileCheck %s`：FileCheck 从**同一个文件**里读出所有 `// CHECK...` 注释，按规则去匹配输出。
3. 全部匹配 → 测试通过。

## 要用到的知识

| 指令 | 语义 |
|---|---|
| `CHECK: pat` | 从当前位置往后找 pat |
| `CHECK-NEXT: pat` | 必须在上一个匹配的**下一行** |
| `CHECK-SAME: pat` | 必须在上一个匹配的**同一行**、它之后 |
| `CHECK-NOT: pat` | 在上一个匹配和下一个正向匹配之间**不能出现** |
| `CHECK-LABEL: pat` | 先用所有 LABEL 把输入切成块，其他 CHECK 不能跨块（一个函数一个块） |
| `CHECK-DAG: pat` | 连续的一组 DAG 可以任意顺序匹配（但不能重叠） |
| `CHECK-COUNT-n: pat` | 连续匹配 n 次 |
| `{{regex}}` | 一段正则 |
| `[[NAME:regex]]` / `[[NAME]]` | 捕获 / 引用变量；`[[$NAME]]` 在 `--enable-var-scope` 下也能跨 LABEL |

模式里的空白序列匹配输入里的任意空白序列，其余字符都按字面匹配（所以 `#ttg.blocked<{` 不用转义）。

::: flow FileCheck 怎么扫描输出
cfg cw=200 nw=172
n src 0 0 "测试文件" "// CHECK... 注释" k=acc
n parse 1 0 "parse_checks" "(kind, pattern, 行号)" k=warn
n lab 2 0 "按 LABEL 切块" "@transpose | @other" k=vio
n blk 3 0 "块内顺序匹配" "pos 只往前走" k=teal
n not 3 1.2 "CHECK-NOT" "检查两个匹配之间" k=pass
n out 1 1.2 "triton-opt 输出" "" k=dark
e src -> parse
e parse -> lab
e out -> lab
e lab -> blk
e blk -> not dash
cap: 关键是“当前位置” pos：每个正向匹配都把它推到匹配末尾，NOT 被挂起，直到下一个正向匹配确定了检查区间的终点。
:::

::: callout analogy 对答案的方式
FileCheck 不是逐字比较整份输出（那样任何无关改动都会打破测试），而是像改卷老师只看几个**关键步骤**有没有、顺序对不对。LABEL 是“第几题”，每道题只在自己的范围里找；NEXT 是“这一步必须紧接着上一步”；NOT 是“这两步之间不许出现某个错误写法”；`[[row_layout]]` 是“你第一问算出来的数，第三问要用同一个”。
:::

## 题目要求

在 `mine/t5_filecheck.py` 里实现（`DIRECTIVE` 正则、`CheckFailure`、`split_input_file` 已给出）：

| 函数 | 要点 |
|---|---|
| `parse_checks(source, prefix)` | `[(kind, pattern, line_no)]`；`COUNT-n` 展开成 n 个 `CHECK`；支持 `--check-prefix` 式的自定义前缀 |
| `compile_pattern(pat, env)` | 转成 Python 正则，返回 `(regex, [捕获的变量名])`；引用未定义变量要报 `undefined` |
| `filecheck(check_source, output, prefix, enable_var_scope)` | 通过返回 True，否则抛 `CheckFailure`，消息里带上失败的 CHECK 行号和种类 |

内部怎么组织随你；参考解用了 `_check_block`（处理一个 LABEL 块）和 `_check_nots`。

## 提示

::: hint 1 compile_pattern
逐字符扫描：遇到 `{{` 找到 `}}`，中间原样放进 `(?:...)`；遇到 `[[`：带 `:` 是捕获，变成命名组 `(?P<name>...)`（名字里的 `$` 要换成合法字符），否则用 `re.escape(env[name])`；空白序列 → `\s+`；其他字符 `re.escape`。
:::

::: hint 2 NEXT 和 SAME 用“行边界”
写一个 `_line_bounds(text, pos)` 返回 pos 所在行的 `[start, end)`。SAME：在上一个匹配的结尾到行尾之间搜。NEXT：取上一个匹配所在行的下一行的边界，在那一行里搜。
:::

::: hint 3 NOT 的区间
遇到 NOT 先挂起；下一个正向匹配（或 DAG 组的最早匹配）确定后，检查 `[上一个匹配的结尾, 这个匹配的开头)`；块结束时，剩下的 NOT 检查到块尾。LABEL：先按顺序找到所有 LABEL 的位置，再对每个块单独跑。
:::

## 在 Triton 仓库里：读一个、改一个、写一个

1. **读**：打开 `coalesce.mlir`，对着 T2 的手算解释每一条 CHECK；用你的 `filecheck()` 跑一遍：`filecheck(open("coalesce.mlir").read(), subprocess.check_output(["triton-opt", ...]))`，和真 FileCheck 结果一致。
2. **改**：故意改坏 `CoalesceUtils.cpp` 里的 `perThread` 计算（比如去掉 `128 / elemNumBits` 的上限），重新 build，用 `lit test/TritonGPU/coalesce.mlir -v` 看哪条 CHECK 先失败、失败信息长什么样。
3. **写**：为 T4 找到的问题（或者 coalesce 的一个没被覆盖的情况，比如 `tt.divisibility = 8`）写一个新的 `// -----` 分段测试：输入 IR + RUN 行 + 最少但足够的 CHECK。好的 CHECK 只检查你关心的东西，别把整个输出抄进去。

```bash
cd triton && pip install -e . --no-build-isolation      # 第一次 build
lit -v build/cmake.*/test/TritonGPU/coalesce.mlir        # 或：cd build/cmake.* && ninja check-triton-lit-tests
```

::: answer 自测：为什么 Triton 的 CHECK 里到处是 `[[row_layout:#.*]]` 这种捕获，而不是直接写 `#blocked`？
layout alias 的名字（`#blocked`、`#blocked1`、`#blocked2`）是打印器按出现顺序分配的，一个无关的改动（多出一个 layout）就会让编号整体移位。捕获“那个内容是 `sizePerThread = [1, 4], ...` 的 alias”，后面再用 `[[row_layout]]` 引用，测试只依赖**语义**（layout 的内容和它被用在哪里），不依赖名字。这也是写新测试时最常被 reviewer 指出的问题之一。
:::
