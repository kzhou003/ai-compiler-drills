lede: 一个“更快了 8%”的 PR 能不能被接受，取决于你的测量方法。这道题写一个可以信任的 benchmark harness：warmup、同步、重复取中位数、把编译 / 搜索时间和稳态时间分开，并且只在差异大于噪声时才说“更快”。

## 背景

roadmap 第 9 节对性能 PR 的要求是：“提供设备、版本、warmup、重复次数、median / variance、compile 与 runtime 分离”。这四件事在两个项目里都会遇到：

- **Triton**：第一次调用要 JIT 编译（加上 autotune，可能几秒），之后每次调用只要几微秒。
- **Luminal**：`cx.compile(...)` 里包含 e-graph 饱和和候选搜索（可能几十秒），之后的 `execute` 才是稳态。
- **GPU 是异步的**：`kernel[grid](...)` 返回时 kernel 可能还没开始跑；不先 `torch.cuda.synchronize()` 就读时钟，测到的是 launch 的时间。

::: flow 一次可信的测量
cfg cw=230 nw=170
n wu 0 0 "warmup × N" "JIT、autotune、缓存、频率" k=warn
n s0 1 0 "sync" "排空之前的异步工作" k=teal
n t0 2 0 "t0 = clock()" "" k=acc
n fn 3 0 "fn()" "异步 launch" k=pass
n s1 3 1.2 "sync" "等这次的工作完成" k=teal
n t1 2 1.2 "t1 − t0" "一个样本" k=acc
n st 1 1.2 "median · IQR" "不用 min，不用单次" k=vio
e wu -> s0
e s0 -> t0
e t0 -> fn
e fn -> s1
e s1 -> t1
e t1 -> st "重复"
cap: 两次 sync 缺一不可：开始前不 sync，样本里混进了上一轮的尾巴；结束前不 sync，测到的只是 launch 的 CPU 开销。
:::

| 统计量 | 为什么 |
|---|---|
| **median** | 对偶发的慢样本（被别的进程抢占、频率波动）不敏感；mean 会被一个离群值拖走 |
| **IQR**（q3 − q1） | 噪声的尺度；两次测量的 IQR 区间重叠，就不能说谁更快 |
| p20 / p80 | Triton autotuner 用 `quantiles=(0.5, 0.2, 0.8)` 报告的就是这三个 |
| CV（stdev / mean） | 稳定性；CV 大于几个百分点时，先修环境再谈优化 |
| Tukey fences | `[q1 − 1.5·IQR, q3 + 1.5·IQR]` 外面的样本标为离群 |

::: callout analogy 量体重
早上起床量一次体重，说明不了你瘦了没有：喝没喝水、穿没穿鞋都会差一公斤。可信的做法是：每天同一时间（同步点）、先站稳（warmup）、连续量一周取中位数，再和上周的中位数比；两周的波动范围（IQR）还重叠，就别急着宣布减肥成功。“第一次量”还包括了找体重秤、开机的时间——那是 compile time，要单独记。
:::

| 函数 | 要点 |
|---|---|
| `percentile(xs, q)` | 线性插值，和 numpy 默认一致 |
| `summarize(samples)` | n、median、mean、stdev、min、max、p10、p90、q1、q3、iqr、cv |
| `bench(fn, warmup, repeats, timer, sync)` | warmup 不计时；每个样本前后各 sync 一次；warmup 之后也 sync 一次 |
| `compile_vs_run(make_fn, repeats, timer, sync)` | `make_fn()` 的构造时间 + 第一次调用 = 一次性成本；之后的中位数 = 稳态 |
| `outliers(samples, k)` | Tukey fences 之外的下标 |
| `compare(base, new)` | `speedup = base.median / new.median`；IQR 不重叠才判 faster / slower |

## 提示

::: hint 1 percentile
排序，`pos = (n − 1)·q/100`，在 `s[floor(pos)]` 和 `s[floor(pos)+1]` 之间线性插值。`[1, 2, 3, 4]` 的 25 分位是 1.75。
:::

::: hint 2 sync 的次数
测试数的是：warmup 之后 1 次，每个样本前后各 1 次，共 `1 + 2·repeats` 次。
:::

::: hint 3 compile_vs_run 与 compare
`compile_vs_run`：`sync(); t0 = timer(); fn = make_fn(); fn(); sync(); first = timer() − t0`，然后对 `fn` 跑一次 `bench`，`one_time_cost = first − steady_median`。`compare`：区间 `[q1, q3]` 重叠 ⇔ `not (new.q3 < base.q1 or base.q3 < new.q1)`。
:::

## 在 RTX 3070 上：测出 launch-bound 到 memory-bound 的拐点

```python
import torch, triton
from solutions.k2_bench_harness import bench, compare
for n in [2**k for k in range(10, 27, 2)]:
    x = torch.randn(n, device="cuda"); y = torch.randn_like(x)
    r = bench(lambda: x + y, warmup=20, repeats=100, sync=torch.cuda.synchronize)
    print(f"{n:>10} {r['median']*1e6:8.1f} us  {3*4*n/r['median']/1e9:7.1f} GB/s  cv={r['cv']:.2%}")
# 再和 triton.testing.do_bench(lambda: x + y, quantiles=(0.5, 0.2, 0.8)) 的结果对比
```

小向量时 median 基本不变（launch-bound），GB/s 随 n 线性上升；大到几百万元素后时间开始随 n 线性增长，GB/s 接近 448 GB/s 的上限（memory-bound）。注意 `time.perf_counter` + `synchronize` 测的是包括 launch 的端到端时间，`do_bench` 用 CUDA event 并在每次之间清 L2 缓存，两者在小 n 时会有差别。

::: answer 自测：为什么报告 min 不如报告 median？
min 是“最幸运的一次”：缓存恰好热、频率恰好高、没有被打断。它不可复现，也不代表用户会看到的时间。median 是典型值，配上 IQR 还能说明可信度。roadmap 的 T3 也特意强调：“不要只报告最快一次；报告 median 和稳定性。”
:::
