lede: 饱和之后 e-graph 里有成千上万个等价程序，选哪一个？Luminal 的 CUDA backend 不信成本公式，而是编译、运行、计时。这道题实现它的搜索骨架：genome（每个 e-class 选一个 e-node）、遗传算法、按实测纳秒的 rank_insert、带验证的 finalists 遍历；再把“代理成本”和“实测”放在一起，量出代理的相关性和它会犯的错。

## 背景

roadmap 的 L3：“对一个小 graph 改变可用 rewrite / 搜索预算 / timeout，记录候选数、搜索时间、最终 latency。交付：search trade-off 报告。”读源码要区分三样东西：**cost proxy**、**compile / search time**、**steady-state runtime**。

真实代码里的对应物：

- [[luminal:src/extraction.rs@pub struct Genome|Genome]]：“per-LayoutTensor-class producer selection”，一个 `ClassId → ProducerChoice` 的映射。
- [[luminal:crates/luminal_cuda_lite/src/search.rs@fn rank_insert|rank_insert]]：只保留 `keep` 个最快的 `(nanos, genome)`，按纳秒升序。
- [[luminal:crates/luminal_cuda_lite/src/finalists.rs@pub struct PendingFinalist|PendingFinalist]]：“1-BASED rank in the GA's ordering”，metric 是“measured nanoseconds”；一个 finalist 被拒绝（例如 arena 超过设备内存预算），就走到下一名。
- [[luminal:crates/luminal_cuda_lite/src/search.rs@pub fn search_implementations|search_implementations]]：整个流程，开头就检查“candidate search requires the `device` feature and a CUDA GPU”。

| 概念 | 本题 | 要点 |
|---|---|---|
| 预算 | `budget`：最多测几个不同的 genome | 重复的 genome 不再测（`fingerprint` 去重） |
| best-so-far 曲线 | `curve` | 单调不增；它的形状告诉你“再多搜一会儿值不值” |
| 代理成本 | `mlp_proxy` | FLOP / 字节模型，分不清手写 tile 和 cuBLASLt，看不见 layout |
| 相关性 | `spearman(proxy, measured)` | 本例约 0.82：大方向对，细节错 |
| finalists | `select_finalist` | fp16 累加在 K=256 时数值不合格，primitive_loop 的 arena 超预算 |
| break-even | `break_even_runs` | 多花的搜索时间要执行多少次才能赚回来 |

::: callout analogy 选餐厅
代理成本像看点评网站的评分：大致靠谱（米其林不会比路边摊差），但分不清两家都是 4.5 分的店哪家今天更好吃。实测搜索像真的去吃：准，但每家都要花一顿饭的时间（预算）。finalists 像订位：排名第一的那家今天满座（验证失败，内存超预算），那就去第二名。break-even 是在问：为了每顿饭好吃一点点，花一个月去试遍全城的餐厅，你要在这个城市住多久才划算？
:::

## 题目要求

在 `mine/l3_search.py` 里实现（空间工具 `space_size / all_genomes / fingerprint / random_genome / mutate / crossover`，以及 `mlp_*` 工作负载已给出）：

| 函数 | 要点 |
|---|---|
| `rank_insert(ranked, nanos, genome, keep)` | 移植 search.rs：满了且不比最差的快就不插；插入位置是第一个比它慢的位置；截断到 keep |
| `genetic_search(space, measure, budget, population, keep, seed, mutation)` | 先测 `population` 个随机 genome，然后循环：从 ranked 里选两个父代 → crossover → mutate → 测（已测过的跳过）；连续 50 次没有新 genome 就停 |
| `proxy_search(space, proxy, measure, k)` | 按代理排序全部 genome，只测前 k 个 |
| `spearman(xs, ys)` | 秩相关，并列取平均秩 |
| `select_finalist(ranked, validate)` | `(rank, nanos, genome, rejected)`；全部被拒抛 `RuntimeError("no finalist ...")` |
| `break_even_runs(search_a, lat_a, search_b, lat_b)` | `(search_a − search_b) / (lat_b − lat_a)`；a 不更快时返回 inf |

## 提示

::: hint 1 rank_insert 的等号
`nanos >= ranked[-1][0]` 时不插（和 Rust 版一致：相等也不能挤掉别人）；插入位置用 `nanos < metric` 找第一个，所以相等的新来者排在已有者之后。
:::

::: hint 2 genetic_search 的计数
用字典 `seen[fingerprint] = ns` 同时做缓存和计数；`evaluate` 在 `len(seen) >= budget` 时直接返回。每测一个新 genome 就 `rank_insert` 并把 `ranked[0][0]` 追加到 `curve`。测试用 `seed=0, budget=10` 检查你恰好测了 10 个、曲线单调、找到了 95 ns 的最优。
:::

## 在 Luminal 里：search trade-off 报告

```bash
# 在 CUDA 机器上，对一个小 graph（例如 crates/luminal_cuda_lite/examples 里最小的那个，或你自己的 MLP）
SEARCH_LOG=1 LUMINAL_SEARCH_OP_NAMES=1 LUMINAL_SEARCH_SEED=0 cargo run --release -p luminal_cuda_lite --example <name> --features device 2>&1 | tee search.log
SEARCH_LOG=1 LUMINAL_SEARCH_SEED=1 ...    # 换种子
SEARCH_MEMORY_MIB=256 ...                 # 收紧内存预算，看 finalist 拒绝 / fallback 行
```

报告里要有：每次运行的候选数、搜索时间、最终 latency、best-so-far 曲线（从 `SEARCH_LOG` 的 best-so-far 行整理）、被拒的 finalist 及原因，以及一个 break-even 估计。以当前 README 和 `CompileOptions` 实际支持的开关为准——如果某个参数（比如搜索预算）只能在代码里改，就在报告里注明改了哪一行。

::: answer 自测：为什么 proxy_search 的前 3 名全军覆没，而 GA 找到了合格的第 3 名？
代理成本认为 fp16 累加更便宜（−5），所以它的前 3 名全是 fp16 累加；但 validation 认为 fp16 在 K=256 时不满足容差，全部拒绝。GA 实测了更多样的 genome，ranked 里保留了 fp32 的候选，finalist 遍历到第 3 名时找到了合格的 103 ns 方案。教训：**排名和验证要分开，且排名之后要留足够多的候选**——这正是 finalists.rs 存在的原因。
:::
