## 背景

roadmap 的共同知识表里，GEMM tiling 的练习输出是“手算 tile 的 FLOPs、数据搬运量和资源占用”。这件事有两个用处：

1. **预测**：扫参数之前就能排除跑不了的配置（shared memory 超限、寄存器 spill），并大致知道哪些配置值得测。这正是 Triton autotuner 的 `early_config_prune` 和 `perf_model` 在做的事（T3）。
2. **解释**：Nsight Compute 报告里的 registers、shared memory、achieved occupancy、DRAM bytes，每一项都能和你算的数对上；对不上的地方，往往就是编译器做了你没想到的事（或者有 bug）。

## 要用到的知识

一个 tiled GEMM 让每个 CTA 负责 C 的一块 `BM × BN`，沿 K 每次搬 `A[BM×BK]` 和 `B[BK×BN]` 进 shared memory。

| 量 | 公式 | 说明 |
|---|---|---|
| FLOPs | `2·M·N·K` | 每个 (m, n, k) 一次乘一次加 |
| 最少字节 | `(MK + KN)·in + MN·out` | 每个矩阵只读 / 写一次 |
| 实际字节（不计 L2） | `MK·⌈N/BN⌉·in + KN·⌈M/BM⌉·in + MN·out` | A 每列 tile 读一遍，B 每行 tile 读一遍 |
| shared memory | `num_stages·(BM·BK + BK·BN)·in` | 流水线有几级，就有几份缓冲 |
| 寄存器（一阶估计） | `BM·BN / 线程数 + 40` | fp32 累加器摊到每个线程，再加地址、计数器、操作数片段 |
| 每 SM 的 CTA 数 | `min(线程限制, 寄存器限制, smem 限制, 16)` | 最小的那一项就是 **limiter** |
| wave | `⌈tiles / (SM 数 × 每 SM CTA 数)⌉` | 最后一轮可能大半空着（tail effect） |

::: flow 一个配置的账：从 tile 到 limiter
cfg cw=225 nw=190
n cfg 0 0.6 "TileConfig" "BM BN BK warps stages" k=acc
n sm 1 0 "shared memory" "stages·(BM·BK+BK·BN)·2" k=teal
n rg 1 1.2 "寄存器 / 线程" "BM·BN/线程 + 40" k=vio
n occ 2 0.6 "每 SM 几个 CTA" "min(四个上限)" k=warn
n wv 3 0 "wave 数" "⌈tiles / (46·CTA)⌉" k=pass
n rf 3 1.2 "roofline" "max(算, 搬) + launch" k=pass
e cfg -> sm
e cfg -> rg
e sm -> occ
e rg -> occ
e occ -> wv
e cfg -> rf dash
cap: 例：128×128×64、4 warp、3 stage 的 fp16 配置，shared memory = 3·(128·64+64·128)·2 = 98,304 B，RTX 3070 每 SM 100 KB，所以每 SM 只能放 1 个 CTA，limiter 是 smem。4096³ 的问题有 1024 个 tile、每轮 46 个，需要 23 轮，最后一轮只有 12/46 满。
:::

::: callout analogy 搬家公司排班
一个 CTA 是一辆货车加一组工人，SM 是停车位。货车越大（tile 越大），每趟搬得越多、来回越少（数据复用高），但一个车位只停得下一辆（occupancy 低）。车位总数固定（46），货物分成 1024 车，就要排 23 轮；最后一轮只有 12 辆车在干活，其他车位空着——这就是 wave 的尾巴。K1 就是在出车前把这些数都算出来。
:::

## 提示

::: hint 1 先写最简单的四个
`gemm_flops`、`gemm_min_bytes`、`smem_bytes`、`threads` 都是一行公式。`tiled_bytes` 注意用 `ceil`：100 行的问题配 64 行的 tile，B 也要被读 2 遍。
:::

::: hint 2 occupancy 的四个上限
`threads: max_threads_per_sm // t`，`regs: regs_per_sm // (regs · t)`，`smem: smem_per_sm // smem`，`blocks: max_blocks_per_sm`。先检查两个“根本跑不了”的情况（smem 超过 `smem_per_block`、寄存器超过 255），再取最小值。同为最小时按名字排序，保证 limiter 确定。
:::

::: hint 3 roofline 和 waves
`roofline`：`t = max(flops/peak_flops, bytes/peak_bw)`；若 `t < launch_overhead`，`bound = "launch"`、`time = launch_overhead`。`waves`：`tiles = ⌈M/BM⌉·⌈N/BN⌉`，`per_wave = sm_count · blocks_per_sm`，最后一轮的填充率 `= (tiles − (waves−1)·per_wave) / per_wave`。
:::

::: answer 自测：为什么不计 L2 的模型会说 4096³ GEMM 是 memory-bound？
128×128 的 tile 下，A 和 B 各被重复读 32 次，`tiled_bytes` ≈ 2.2 GB，448 GB/s 要 4.9 ms，比 40 TFLOP/s 下的 3.4 ms 计算时间还长。但真实 GPU 上同一列 tile 的 CTA 几乎同时在读同一块 A，绝大部分重复读取会命中 4 MB 的 L2，真正到 DRAM 的字节接近 `gemm_min_bytes`（约 100 MB），于是变成 compute-bound。这就是 Triton tutorial 里做 **grouped ordering**（`GROUP_SIZE_M`）的原因：让同时运行的 CTA 共享更多 A/B tile，提高 L2 命中率。T3 的测试特意保留了这个“错误”的结论，提醒你模型的边界在哪里。
:::
