lede: 把 y = relu(x @ w + b) 交给 Luminal，它记录下来的不是三个“大算子”，而是十几个 primitive 节点：broadcast 视图、一个 [M, N, K] 的 Mul、一个 ReduceSum、一个 LessThan 和一个 Select。这道题用 Python 写一个 Luminal 式的“只记录、不计算”的图，给出节点语义表，再写一个按拓扑序执行的 reference runtime。

## 背景

roadmap 的 L1：“构建 y = relu(x @ w + b)，标出 shape、dtype、broadcast 和每个 primitive。交付：graph DAG + 节点语义表。”

真实 Luminal 里这件事由 `GraphTensor` 的方法完成：

- [[luminal:src/frontend/matmul.rs@pub fn matmul|matmul]]：“broadcast + reduce in the operands' shared dtype, NOTHING else”——把两个操作数映射到 `[..., M, N, K]`，相乘，沿 K 求和；从不插入 cast。
- [[luminal:src/frontend/unary.rs@pub fn relu|relu]] = `maximum_f32(0.)`；[[luminal:src/frontend/binary.rs@pub fn maximum|maximum]] = `lt(...).select(...)`，外加一个 NaN 覆盖（注释解释了为什么不用 `fmax`）。
- [[luminal:src/frontend/unary.rs@pub fn exp|exp]] = `(x · log2(e)).exp2()`：primitive 集里只有 `Exp2`。

cap: 灰色的 Expand / Permute 只改变索引方式，不搬数据。真正“贵”的是 Mul：如果每个节点都物化成一个 buffer，`[M, N, K]` 的乘积会占 M·N·K·4 字节——这正是 Luminal 需要 e-graph 和搜索，把 Mul + ReduceSum 合成一个 GEMM（或者交给 cuBLASLt）的原因。
:::

| 规则 | 说明 |
|---|---|
| broadcast 是显式的 | 二元 op 要求两边 shape 完全一致；`b[N]` 加到 `[M, N]` 上前要先 `Expand` |
| 记录不计算 | `x + y` 只往 `graph.nodes` 里追加一个节点，返回一个只含 id 的句柄 |
| dtype 随节点走 | `LessThan` 产出 `bool`；`Select` 的 dtype 跟随两个分支 |
| 拓扑序执行 | reference runtime 从输出反向 DFS，得到“每个输入都在使用者之前”的顺序 |

::: callout analogy 录音而不是现场演奏
PyTorch eager 像现场演奏：每写一行，乐手就弹一个音（`x + y` 立刻算出结果）。Luminal 像录音棚里先把整首曲子写成**分轨乐谱**（DAG），而且所有乐器都被拆成几种基本音色（primitive）。写完之后编曲（e-graph + 搜索）可以重新安排：把两条轨合并成一个和弦（fusion），用采样代替真乐手（cuBLASLt）。reference runtime 就是按乐谱老老实实一轨一轨弹一遍，用来核对编曲之后的版本有没有弹错（L5）。
:::

|---|---|

## 提示

::: hint 1 matmul 的两个 view
A 是 `[M, K]`，在第 1 维插入 N：`[M, N, K]`。B 是 `[K, N]`，先转置成 `[N, K]`，再在第 0 维插入 M：`[M, N, K]`。两者逐元素相乘，沿最后一维求和得到 `[M, N]`。
:::

::: hint 2 run 里的 Expand
`np.broadcast_to(np.expand_dims(a, axis), node.shape)`：先插一个长度 1 的轴，再广播成目标形状。`broadcast_to` 返回的是 view，不复制数据，和 Luminal 的语义一致。
:::

::: hint 3 materialized_bytes 的数
`build_mlp(64, 256, 64)`：Mul 是 64·64·256 个元素，ReduceSum、Add、LessThan、Select 各 64·64 个，乘 4 字节，测试里写成 `(64·64·256 + 4·64·64)·4`。
:::

## 在 Luminal 里：看真正的图

```rust
use luminal::prelude::*;
let mut cx = Graph::new();
let x = cx.tensor(vec![2, 3], DType::F32);
let w = cx.tensor(vec![3, 4], DType::F32);
let b = cx.tensor(vec![4], DType::F32);
let y = (x.matmul(w) + b.expand_rhs(vec![2, 4])).relu().output();
// 编译前后都可以导出可视化：src/visualization.rs；编译时 EGGLOG_DEBUG=1 会把 egglog 程序也打印出来
```

对照你的语义表：真实图里每个操作数的 broadcast 是**一个** view map 节点（matmul.rs 调用 [[luminal:src/frontend/movement.rs@fn record_view_map|record_view_map]]，注释说“Record ONE view apply ... no intermediate movement scaffolding”），而不是一串 Expand / Permute；`relu` 会多出 NaN 覆盖那一个 `Select`。这些差异正好说明：primitive 集合的设计（README 的 15 个 vs `LogicalOp` 的完整列表）本身也在演进，读代码时以 pin 住的 commit 为准。

::: answer 自测：为什么 broadcast 不复制数据也能被“搜索”？
broadcast 只是索引映射：`b_expanded[m, n] = b[n]`。它在图里是一个节点，所以 e-graph 可以对它做改写（比如把 `Add(ReduceSum(Mul(...)), Expand(b))` 识别成“带 bias 的 GEMM”，匹配到 cuBLASLt 的 `EPILOGUE_BIAS`）；而它在执行时可以不分配任何内存。把“改变索引”和“搬数据”分开，是 Luminal 能自动发现 fusion 的前提。
:::
