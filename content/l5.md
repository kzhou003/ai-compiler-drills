**容差怎么定（要写进测试的那句理由）**

- 输出要舍入到存储 dtype：相对误差最多半个 ulp，取 `2·eps(dtype)` 留余量。
- 长度 n 的 fp32 求和：约 `√n · eps32`，取 `4·eps32·√n`。
- `rtol = 2·eps(dtype) + 4·eps32·√n`；softmax 的输出在 [0, 1]，很多概率接近 0，相对误差没有意义，所以 `atol = max(eps(dtype) / n, 1e-7)`。

**三个 bug，三种教训**

| bug | 现象 | 什么输入能抓到 |
|---|---|---|
| `tail`：最后一个不满的块没进求和 | 结果整体偏大 | n 不是 64 的倍数且 > 64（`edge_sizes` 里的 65、97、129…） |
| `fp16_acc`：在存储 dtype 里累加 | 误差 1e-5 量级，fp32 容差能抓到 | 任何长度；fp32 输入最明显 |
| `no_max_sub`：没有先减最大值 | exp 溢出成 inf，输出 NaN | **只有大输入**：N(0, 3) 永远抓不到，scale = 40 才抓到 |

::: callout analogy 质检抽样
差分测试是工厂质检：同一批原料（同一组舍入后的输入）同时送进“标准样机”（Reference）和“新生产线”（CUDA），比较产品。只抽“正常尺寸”的零件（随机正态输入），可能永远发现不了“超大零件会卡住机器”（溢出）的问题；质检方案必须专门放进边界件：刚好多出一点的尺寸（n = 65）、极端的数值（大 logits）。容差理由就是质检标准上那句“允许误差 ±x，因为……”。
:::

## 在 Luminal 里：写一个真的

1. 选一个 op：softmax、`gelu`、`log_softmax`，或任何在 `src/logical/op/` 下的 primitive。
2. 在 `crates/luminal_cuda_lite/tests/` 下照着已有文件的写法：同一张图分别 compile 到 `ReferenceRuntime` 和 CUDA runtime，同样的数据，比较输出。`emit_rust_test` 生成的是骨架，其中 `random_vec_seeded`、`run_reference`、`run_cuda`、`assert_close` 要替换成仓库里实际的 helper。
3. 参数覆盖：`edge_sizes(64)` 那组长度、F32 / F16 / Bf16、一个大 scale 的用例。
4. PR 描述里写上：GPU、driver、Toolkit、commit、容差理由（直接用 `tolerance_for` 的 `why`）。

::: answer 自测：如果 CUDA 和 Reference 差了 2 个 ulp，你会提 bug 吗？
先看容差理由。softmax 输出舍入到 fp16 就可能差 1 个 ulp，fp32 求和顺序不同又会带来 `√n·eps32` 量级的差异，所以 2 ulp 通常在合理范围内，不是 bug。真正值得报告的是：超出有理由的容差、NaN / inf 位置不同（`check_close` 的 NaN mismatch），或者误差随 n、随 scale 明显超线性增长——那往往意味着累加精度或数值稳定性有问题，就像 `fp16_acc` 和 `no_max_sub`。
:::
