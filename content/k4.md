lede: Fusion 省掉 launch、省掉中间结果在 DRAM 里的往返，但把更多东西塞进一个 kernel 的寄存器里。这道题把这笔账写成代码：给一条算子链和一个切分方案，算出字节数、launch 次数和寄存器峰值，再枚举所有切法找最快的。

## 背景

roadmap 的共同知识表：“Fusion：减少 launch / intermediate traffic 与 register pressure 的 trade-off — 对比 unfused 与 fused epilogue”。

- 在 **Triton** 里，fusion 就是把 bias、activation、residual 写进 GEMM kernel 的 epilogue：累加器还在寄存器里时就把后续 elementwise 做完，只写一次结果。
- 在 **Luminal** 里，fusion 是图级的选择：cuBLASLt 可以带 `CUBLASLT_EPILOGUE_RELU_BIAS` 一次完成 matmul + bias + relu（[[luminal:crates/luminal_cuda_lite/src/ops/cublaslt/device_call.rs@CUBLASLT_EPILOGUE_RELU_BIAS|cublaslt/device_call.rs]]），也可以拆成三个 launch；搜索（L3）决定用哪种。

## 要用到的知识

把链切成若干段，每段一个 kernel：

- 一段读的字节 = 段内所有 stage 的**外部输入**（权重、bias、residual）+ 上一段的输出；写的字节 = 段内最后一个 stage 的输出。
- 段内的中间结果只在寄存器里，不进 DRAM。
- 一段的寄存器峰值 = 段内各 stage 的 `live_regs` 之和；超过 255 就会 spill，本题用“访存时间 × spill_penalty”粗略模拟。
- 每段一次 launch（约 5 µs）。n 个 stage 有 `2ⁿ⁻¹` 种切法。

::: flow GEMM + bias + GELU + residual：不融合 vs 融合
cfg cw=180 nw=150 rh=92
n mm 0 0 "matmul" "写 C 到 DRAM" k=acc
n b 1 0 "bias" "读 C，写 C′" k=warn
n g 2 0 "gelu" "读 C′，写 C″" k=warn
n r 3 0 "residual" "读 C″ + R，写 Y" k=warn
n fused 1 1.3 "一个 kernel" "累加器 → 寄存器里做完 → 写 Y" k=pass w=1.9
e mm -> b "MN"
e b -> g "MN"
e g -> r "MN"
cap: 4096² 的 fp16 例子：不融合时 C 在 DRAM 里往返三次，总流量 335,552,512 B，4 次 launch；全部融合后 134,225,920 B，1 次 launch，寄存器峰值从 128 升到 160。
:::

::: callout analogy 做菜的盘子
不融合像每做完一步就把菜盛到盘子里端上桌（写 DRAM），下一步再从桌上端回来（读 DRAM）：切好的菜装盘、端回来炒、炒好装盘、端回来调味。融合就是在一口锅里连续做完再装一次盘。但锅的大小有限（寄存器）：如果每一步都要占很多锅边的位置，锅里放不下就只能临时往外盛（spill），反而更慢。
:::

## 在 RTX 3070 上对照

把 tutorial 03 的 matmul 改成两个版本：(a) epilogue 里做 `+ bias`、`gelu`、`+ residual`；(b) matmul 只写 C，再用三个 elementwise kernel。用 K2 的 harness 量 4096² 和 16×4096 两个形状，并在 `ncu` 里看 DRAM bytes：大形状的差距接近流量之比，小形状的差距接近 launch 次数之比。

::: answer 自测：什么时候不该融合？
当融合后的 kernel 寄存器超出上限而 spill，或者融合迫使一个 kernel 用不适合某一部分的 tile / layout 时（例如把一个需要整行数据的 softmax 塞进按 tile 切的 GEMM epilogue）。测试里的 `heavy` 链（live_regs 200 + 100）在 `spill_penalty=3` 时，拆成两个 kernel 反而更快。Luminal 不预设答案，而是把融合和不融合都放进搜索空间实测。
:::
