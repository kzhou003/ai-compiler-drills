## 要用到的知识

| dtype | 尾数位 | eps（1 附近的间距） | 典型用途 |
|---|---|---|---|
| fp32 | 23 | 2⁻²³ ≈ 1.2e-7 | 累加器 |
| fp16 | 10 | 2⁻¹⁰ ≈ 9.8e-4 | 存储 / Tensor Core 输入，范围小（最大 65504） |
| bf16 | 7 | 2⁻⁷ ≈ 7.8e-3 | 存储，范围和 fp32 一样 |

- **ULP 距离**：把浮点数映射成“按大小排序的整数”（符号-数值 → 补码的技巧），两数之差就是中间隔了几个可表示值。`-0.0` 和 `+0.0` 相距 0 ULP。
- **容差为什么随 √k 增长**：长度 k 的求和，每一步的舍入误差大致随机，累积误差像随机游走，约 `√k · eps`。所以 `rtol = c · eps · √k`。
- **`|a − e| ≤ atol + rtol·|e|`**：接近 0 的值相对误差没有意义，靠 atol 兜底。

::: callout analogy 用不同的尺子量
fp32、fp16、bf16 像刻度分别是 0.1 mm、1 mm、1 cm 的尺子。用 1 cm 刻度的尺子量出来差 3 mm，不能说测量错了；但用 0.1 mm 的尺子差 3 mm 就该查一查了。容差就是“这把尺子、量这么长的东西，合理的误差范围”——尺子越粗、量的段数越多（归约越长），容差越大。
:::

## 提示

::: hint 1 ULP：把位模式变成有序整数
fp32：`i = a.view(np.int32)`；正数的位模式本身就是递增的，负数要翻转：`i < 0` 时取 `-(i & 0x7FFFFFFF)`。这样 `-0.0` 和 `+0.0` 都映射到 0。fp16 同理（`int16`、`0x7FFF`）。bf16 是 fp32 的高 16 位：`to_bf16(a).view(np.uint32) >> 16`，符号位是 `0x8000`。
:::

::: hint 2 check_close 的顺序
先比形状，再比 NaN 位置（`np.isnan(a) != np.isnan(e)`），然后在非 NaN 的位置算 `diff` 和 `allowed = atol + rtol·|e|`。`index` 取 `argmax(diff − allowed)` 并 `unravel_index`。
:::

::: hint 3 为什么 fp16 matmul 用 fp32 容差一定失败
测试里 `a.astype(float16) @ b.astype(float16)` 把输入舍入到了 fp16，单这一步的相对误差就有 `2⁻¹¹`，远大于 `2·2⁻²³·√512`。用 `tolerance("float16", k, c=4)` 并把 atol 再乘 `√k`（结果的量级约为 `√k`）就能通过。
:::


你会看到 `"ieee"` 能过 `tolerance("float32", 512)`，`"tf32"` 只能过接近 `tolerance("bfloat16", 512)` 量级的容差（TF32 有 10 位尾数，比 bf16 还多 3 位，但远少于 fp32）。这就是为什么 PR 里的数值测试必须写明 dtype、精度模式和容差理由。

::: answer 自测：e-graph 证明了 (a+b)+c ≡ a+(b+c)，为什么编译器还要小心使用这条规则？
e-graph 里的“等价”是**实数代数**上的等价。在浮点里，结合律不成立：`(1e8 + (−1e8)) + 1 = 1`，而 `1e8 + ((−1e8) + 1) = 0`（fp32 里 −1e8 + 1 舍入回 −1e8）。如果编译器自由使用这条规则，同一个模型在不同搜索结果下数值会不同。实际做法是：只在数值上可接受的场景使用（比如有 fp32 累加器、容差明确），并用 L5 那样的对拍测试兜底。
:::
