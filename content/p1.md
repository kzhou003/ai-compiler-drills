lede: 从“读懂了”到“合进去了”中间隔着一套流程：挑一个小而明确的 issue、先在 issue 里给出环境和最小复现、和维护者对齐方向、最小改动、补测试、给出可复现的证据、回应 review。这一页把这套流程落到 Triton 和 Luminal 的具体入口上，并用 Luminal #370 做一次完整演练。

## 挑任务：五个筛子

| 筛子 | 问自己 |
|---|---|
| 模块 | 是我练过的部分吗（coalesce / layout / 测试 / CUDA backend / 对拍）？ |
| 硬件 | 能在 RTX 3070（SM86）上复现吗？需要 Hopper / Blackwell 的先放一放 |
| 复现性 | 我能写出一个 T4 / L5 那样的最小复现吗？ |
| 已有 PR | 有没有人已经在做？搜 issue 编号和关键词 |
| 维护者响应 | 近期类似的 issue / PR 有人回复吗？ |

**不要同时认领两个大规模 feature。** 先在 issue 里提供环境与最小复现，问清预期方向，再动手。

## Luminal 入口与 #370 演练

[luminal #370](https://github.com/luminal-ai/luminal/issues/370)：“luminal_cuda_lite fails to compile on CUDA 13.x (v1 graph dependency APIs missing)”，写这一页时仍是 open。roadmap 的建议是先用它做 CUDA 环境验证：仍然存在且范围小，就作为第一笔贡献候选；已经修复或与你的环境无关，就从 open issues 里挑一个 reference-vs-CUDA correctness test（L5）。

演练步骤：

1. **读 issue**：报告的是 CUDA 13 移除 / 改名了某些 v1 的 CUDA graph 依赖 API。Luminal 的 graph 捕获代码在 [[luminal:crates/luminal_cuda_lite/src/cuda_graph.rs|cuda_graph.rs]]；CUDA 绑定来自 cudarc 的 fork（[[luminal:crates/luminal_cuda_lite/Cargo.toml@cudarc|Cargo.toml 里的 cudarc 依赖]]，feature 包含 `cuda-version-from-build-system`）。
2. **记录环境**：`nvcc --version`（Toolkit 是不是真的 13.x，而不是 `nvidia-smi` 显示的 13.x）、`CUDA_HOME`、`cargo -V`、`git rev-parse HEAD`。
3. **在当前 main 上复现**：`cargo build -p luminal_cuda_lite --features device`，保留完整日志。
4. **定位**：编译错误指向哪个符号？它在 cudarc 里还是在 Luminal 自己的代码里？CUDA 13 的 release notes 里这个 API 的替代是什么？
5. **评估范围**：是改 Luminal 一处调用（小），还是要改 cudarc fork（要和维护者确认）？
6. **在 issue 里回复**：环境、复现命令、错误摘录、你的定位和打算的修法，问维护者是否认可方向。

## PR 应该长什么样

无论哪个项目，PR 描述固定包含：**Problem**（实际行为、预期、影响）、**Minimal reproducer**（代码、shape、dtype、GPU、commit SHA）、**Root cause**（哪个 pass / backend / rewrite / dispatch）、**Fix**（最小改动，为何不破坏其他路径）、**Tests**（regression、reference comparison、相关 suite）、**Performance evidence**（如果宣称更快：设备、版本、warmup、重复次数、median / variance、compile 与 runtime 分离）。

```markdown
## Summary
- What is broken or inefficient?
- Which compiler/backend stage is responsible?

## Reproducer
- Commit:
- GPU / driver / CUDA Toolkit:
- Shape / dtype:
- Minimal command:

## Root cause
- Relevant IR / pass / backend path:

## Fix
- Why this change is correct:
- Other backends / dtypes affected:

## Validation
- Tests:
- Before / after benchmark (if applicable):
```

::: callout analogy 看病
好的 issue 像一份清楚的病历：症状（实际 vs 预期）、什么时候发作（最小复现）、病人的基本情况（环境快照）。好的 PR 像一份手术方案：病因在哪（root cause）、只切该切的地方（最小改动）、术后怎么确认好了（tests）、有没有副作用（其他 backend / dtype）。维护者是主任医师：先让他们看病历、认可方案，再上手术台。
:::

## review 节奏（Week 12）

- 回应每一条评论；同意就改，不同意就给出数据或理由。
- reviewer 要求拆分，就拆：一个 PR 只做一件事。
- 补齐 CI、format（Triton 用 pre-commit；Luminal 用 `cargo fmt` / `cargo clippy`）。
- 性能 PR 给出稳定的 before / after（K2 的 `compare` 判定“faster”而不是“within noise”）。

::: answer 自测：为什么建议第一笔贡献是“测试”而不是“优化”？
测试的价值容易验证（失败 → 修复后通过），改动小、风险低，维护者审起来快；它还迫使你搞懂相关代码路径和测试基础设施。优化需要稳定的 benchmark 证据、要说明对其他 backend / 形状 / dtype 没有回退，审查成本高，也更容易和维护者的规划冲突。roadmap 原话：“避免没有数据支持的性能优化”。
:::
